3. WHAT IS BROKEN — CONFIRMED (FUNCTIONAL, user-visible) — task status filter is a no-op
  File:   cli/api_client.py:100
  Code:   params["Completed"] = completed
  The backend expects the query param `completed` (backend/main.py:151).
  Sending "Completed" means FastAPI silently ignores it and returns ALL
  tasks instead of the filtered set. Verified live:
      curl ".../tasks?Completed=false"  ->  returned the full task list
      curl ".../tasks?completed=false"  ->  correctly filtered
  Impact:  `flunky task list --completed true|false` is silently broken.
  Fix:     params["completed"] = completed
  Severity: HIGH — it fails silently, returning wrong data with no error.

BUG-2 (LATENT CRASH) — task delete does not assert the 204 status
  File:   cli/api_client.py:168
  Code:   if response.status_code == 200: return response.json()
  The backend correctly returns 204 No Content (backend/main.py:275). The
  client checks for 200, which never happens, so the function falls through
  and returns None silently. Worse: if the server ever DID return 200 the
  call would .json() an empty body and raise. There is also no 401/403/404
  branch, so a permission error is indistinguishable from success — the
  CLI prints "Task deleted successfully!" either way.
  Fix:     accept 200/204, and raise on 401/403/404.
  Severity: MEDIUM — false success message + misleading error handling.

             Recommend failing fast if SECRET_KEY is unset in production.
